# Decisions

Each entry: decision, why, alternatives considered. Newest at the bottom.

## D1. Repo location is the Orca-registered folder
- **Decision:** Use `/Users/hutchida/orca/projects/meeting-prep-agent` (already a git repo registered in Orca) instead of `~/GIT/meeting-prep-agent`.
- **Why:** Orca worktree/agent orchestration needs a registered repo; it is already a fresh local git repo with no remote.
- **Alternatives:** Create `~/GIT/meeting-prep-agent` and register it with `orca repo add` (extra moving part, no benefit).

## D2. LLM model: no Claude Haiku alias exists on the proxy
- **Decision:** `LLM_MODEL` has no Haiku default. The proxy `/models` lists no Haiku alias (Claude entries are Sonnet 4/4.5/4.6/5 and Opus 4.7/4.8 on Vertex). The default is the cheapest tool-calling model that passes measurement in G0b, with `vertex-ai-gemini-3-flash-preview` as the pre-measured candidate (tool calling works, ~1.4 s for a tiny call). Configurable through `LLM_MODEL`.
- **Why:** The $0.05/briefing and 60 s targets are not realistic with Sonnet-class pricing across four sub-agents; a Flash-class model is the nearest in price/latency to Haiku.
- **Alternatives:** `vertex-ai-claude-sonnet-4.6` (works, costs several times more); ask the user (not blocking). Swap by changing one env var.

## D3. Credentials handled locally, never committed
- **Decision:** `LITELLM_BASE_URL` / `LITELLM_API_KEY` were not present in the orchestrator's shell. They were supplied in the build prompt. They are kept only in a gitignored `.env` (mode 600) in the repo root and copied into each task worktree's gitignored `.env`; they never appear in task prompts, reports, recordings, traces or commits.
- **Why:** Workers launched by Orca do not inherit the user's interactive shell environment.
- **Alternatives:** Put them in `~/.zshrc` (changes the user's shell config, not requested).

## D4. Worker agent and model
- **Decision:** Workers run as the `opencode` agent with `github-copilot/claude-sonnet-5.5` (test call confirmed OK). Token/cost metrics may be "unavailable" if the harness does not expose them.
- **Why:** Same signed-in account as the orchestrator; strong coding model.
- **Alternatives:** `claude` CLI agent (not tested for account/billing).

## D5. Python type checker is mypy; web lint uses plain typescript-eslint
- **Decision:** `mypy --strict` for agent/, flat-config ESLint with typescript-eslint for TS.
- **Why:** Simple, offline, no node download (pyright's pip wrapper fetches node).
- **Alternatives:** pyright; eslint-config-next.

## D6. Pydantic models for the contract live in agent/src/mpa/contract/ and are owned by the contract task
- **Decision:** G0b owns `agent/src/mpa/contract/**` (Pydantic models mirroring the JSON Schema) plus `agent/tests/test_contract*.py`.
- **Why:** The contract has a single owner; service tasks import, never redefine, models.
- **Alternatives:** Each service task writes its own models (drift risk).

## D7. Model default after measurement
- **Decision:** `LLM_MODEL` default is `vertex-ai-gemini-3-flash-preview` (fallback `vertex-ai-gemini-3.6-flash`), from `docs/orchestration/measurements.md`: tool calling works, 1.4–1.8 s per call, about US$0.50/$3.00 per 1M tokens in/out, no rate limits seen with 6 concurrent calls. The LLM client omits `temperature` for models that reject it and uses `reasoning_effort: minimal` where thinking tokens would eat `max_tokens`.
- **Why:** Cheapest reliable tool-caller; Claude models on the proxy cost 5–10x more per token. No Haiku alias exists.
- **Alternatives:** `azure/gpt-5-mini` (cheaper per token, rejects `temperature`, slower); Sonnet-class (over the $0.05/briefing target).

## D8. Contract design choices made in G0b
- Timestamps are `YYYY-MM-DDTHH:MM:SS[.sss]Z` (UTC, `Z` only); `Settings` normalises `DEMO_NOW`.
- Email sender field is `sender`. Citations and search hits are one object per type so the id prefix is enforced by schema. Pack sections are a fixed 7-tuple. `Sentence` = `FactSentence` (≥ 1 citation) or `NoteSentence` (`kind: "note"`).
- `ToolResult` = `{items, total_matches, truncated}`; a `get_email` body over 4 KB is truncated by the tool layer with `truncated: true`.
- Generated `models.py` is committed and regenerated by `agent/scripts/gen_models.py` (tested for drift). No hand-written mapping layer exists, so "field only in a mapping" is covered by schema/model/fixture property-set equality tests.
- Enron items keep original dates and real corporate addresses (public CMU release, noise only); synthetic items use `.test` domains.

## D9. How the finished briefing reaches clients (gap found at the G0 gate)
- **Decision:** The 8 KB event cap means a full `BriefingPack` can't travel in one event, and the contract had no way to deliver the final pack. A follow-up contract task (g0c) adds an `assemble_pack(events)` helper (TS + Python) and a fixed event order: `… verifier_result`, then one `draft` event per section (seven, canonical order, only the last has `complete=true`), then `run_done`. Only verified sentences are ever emitted. Full-run event-stream fixtures are added for UI/API/eval development.
- **Why:** Keeps the API to the three specified routes, keeps the UI honest (it never shows unverified text) and gives every consumer one tested assembly function.
- **Alternatives:** `GET /briefings/{run_id}` with server-side storage (extra route and state, evals can't use it); raising the event cap (violates the spec).

## D10. Gate summaries go in the session transcript and docs/orchestration/gate-summaries.md
- **Decision:** No Slack/email/other third-party message is sent for gate summaries; they are printed in the orchestrator session and appended to `docs/orchestration/gate-summaries.md`.
- **Why:** Writing to a real third-party account is on the "ask before" list and no destination was specified.
- **Alternatives:** Slack DM or Mail.app message (needs the user's confirmation of the target).

## D11. Hand-written agent loop, no agent framework
- **Decision:** The tool-use loop, parallel sub-agents, budgets, retries and event emission are plain Python with `asyncio` (`agent/src/mpa/loop`, `agent/src/mpa/agents`). All model calls go through the `LLMClient` interface; no LangChain, LangGraph, CrewAI or vendor agent SDK.
- **Why:** The project exists to show the mechanics (what is retried, what is budgeted, what is cancelled, which event is emitted when). A framework would hide exactly that, and the loop is small (about 400 lines).
- **Alternatives:** A framework graph (less code, less visible behaviour, harder to test offline).

## D12. Retrieval is BM25 over the fake snapshot, behind `DataSource`
- **Decision:** `FakeDataSource` indexes the JSONL files with `rank_bm25` (one index per type, built lazily). A fixed discount (x0.5) is applied to Enron noise and a boost (x1.5) to news items whose `about` field matches the query entity, so same-name companies rank below the client's own news.
- **Why:** Deterministic, offline, millisecond search with no embedding model or vector store, so every test and replay is reproducible. The interface lets Microsoft Graph replace it later (`GraphDataSource` is a documented stub).
- **Alternatives:** Embeddings (needs a model or an index to ship and makes runs less reproducible).

## D13. Verifier: deterministic support check first, model check only for borderline sentences
- **Decision:** A sentence is kept only if its citations exist and support it by a deterministic rule (figures, dates and codes must match exactly; at least half of the content words must appear). Borderline sentences get one batched model check when budget allows, otherwise they are dropped. Sub-agent findings run the same check before the Writer sees them.
- **Why:** The check costs nothing, is reproducible and catches the typical hallucination (a changed figure or date). A model-only check would cost calls on every sentence and would be as non-deterministic as the writer.
- **Alternatives:** Model-based entailment on every sentence (cost, latency, variance). Known cost of the choice: some true sentences that synthesise several sources are dropped, and a true sentence cited to the wrong item can pass.

## D14. Record and replay of model calls, keyed by a hash of the request
- **Decision:** `RecordingClient` stores each call under the SHA-256 of the canonical JSON of model, messages, tools, temperature and max tokens; `ReplayClient` serves it. Tool call ids are normalised (`corr_1`, ...) so provider ids do not change keys. A replay miss fails that agent with reason `error` instead of crashing.
- **Why:** Gives an offline, key-free demo and tests that exercise the real prompts. The cost is that any change to a prompt, to the data or to `LLM_MODEL` invalidates recordings, so they are recorded last.
- **Alternatives:** Canned fake responses (would not exercise the real prompts).

## D15. Rule-based meeting resolution, no model
- **Decision:** The request is mapped to one calendar meeting by client alias from calendar titles, weekday names and the next 14 days from `DEMO_NOW`. Unknown or ambiguous requests produce a short partial briefing that lists candidate meetings.
- **Why:** Cheap, deterministic and testable; the fake dataset has three meetings. Relative words ("today", "tomorrow", "next week") are not interpreted.
- **Alternatives:** A model call to extract the meeting (more flexible, adds a step and variance before any work starts).

## D16. Tracing is optional and self-hosted: Langfuse server v2
- **Decision:** `TRACING=langfuse` sends traces to a local Langfuse v2 (one app container plus Postgres, `docker-compose.yml`, port 3100) through the 2.x Python SDK, installed as the optional extra `langfuse`. The tracer never raises or blocks; if Langfuse is unreachable the app falls back to the no-op tracer with one warning. Content is truncated and scrubbed before it is sent.
- **Why:** v3 needs ClickHouse, Redis and S3-compatible storage; v2 is enough for a demo. Tracing must never be a reason a briefing fails.
- **Alternatives:** Langfuse v3 or a hosted service (heavier or needs credentials); OpenTelemetry only (no LLM-specific UI).

## D17. Conflicting dates: carry unreported chat messages into the findings
- **Decision:** After the Correspondence agent finishes and its findings pass the support check, any chat message it retrieved that states a date or figure, belongs to the client's channel and is cited by no finding is added as a near-verbatim finding ("<author> wrote in <channel> on <date>: <text>", with the author and date taken from the chat record). Capped at 4. The Verifier's rules are unchanged.
- **Why:** Diagnosis of the one-sided Halden Pay go-live date: the chat message with the later date (28 April) was retrieved in every run, but it reached the briefing in 0 of 6 live runs. The agent either left it out or paraphrased it with a month for "the 14th", which the strict date check rightly dropped. The Writer cannot flag a conflict it never sees. After the fix it was cited in 6 of 6 and the disagreement was flagged in 5 of 6, then in 10 of 10 further runs.
- **Alternatives:** loosening the Verifier's date matching (rejected: a changed date is the typical hallucination); a prompt-only change (the prompt already asked for every dated chat message; the small model ignores it); a second pass asking the model to look for conflicts (extra cost and latency).
- **Limits:** the client filter is the first word of the client name in the channel name, which fits this dataset but is a heuristic; a Graph source would need a real thread-to-client mapping.

## D18. The eval judge is a stronger model than the agent
- **Decision:** `make eval` judges with `vertex-ai-claude-sonnet-5` by default (`JUDGE_MODEL` overrides, `JUDGE_MODEL=same` restores the agent's model). Replay-mode evals keep using `LLM_MODEL`.
- **Why:** The first judge was the agent's own model, which can flatter its own output. Sonnet-5 is a different model that handles the strict JSON judge prompts and costs about US$0.48 per full eval run (14 calls), against US$0.04 before.
- **Alternatives:** `vertex-ai-claude-opus-4.8` (about 2.5x the cost); `vertex-ai-claude-sonnet-4.6` (similar, older). The judge is still uncalibrated against human labels; scores before and after the switch are not comparable (average recall 82% with the old judge, 80% with the new one on different runs).

## D19. `make record` regenerates the demo recordings with a quality gate
- **Decision:** `agent/scripts/record_demo.py` records the four demo runs live, replaying anything already accepted so runs sharing a request prefix stay consistent, retries each run up to 6 times until it passes a quality check (all sections filled, at least 3 talking points, at most 2 verifier drops, `partial` only for the outage run, and a flagged conflict where the gold data has one), and replaces `data/recordings/` only if all four pass.
- **Why:** At rehearsal the Brightmoor normal run replayed with an empty "Talking points" section, because the outage run recorded different model text for the same request keys and overwrote the first. This turns that manual fix into a tested command.
- **Alternatives:** `RECORD=1` alone (kept, but unsafe for sets of runs); committing a fixed seed (the provider is not deterministic).
